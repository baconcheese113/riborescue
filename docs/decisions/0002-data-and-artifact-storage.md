# ADR-0002 — Data and artifact storage (no LFS)

**Status:** accepted · **Date:** 2026-07-19 · **Deciders:** Joseph, Mahan

## Context

RiboRescue touches large files (SRA FASTQ, a ~30 GB STAR index, BAMs, a potentially large scored
table), but GitHub LFS gives only ~1 GB free. Committing large files — via LFS or otherwise — is
the wrong model for a reproducible scientific pipeline anyway: the repo should hold *code and the
recipe to regenerate*, not the bytes.

## Decision

**Nothing large goes in git. No GitHub LFS.** Artifacts are classified and routed:

| Artifact | Size | Where it lives | Provenance |
|---|---|---|---|
| Inputs: SRA FASTQ, GRCh38, STAR index, Toledano data, ClinVar | huge | **Fetched from public source** by pipeline scripts into gitignored `data/` | accession IDs + checksums + pinned reference/release versions |
| Intermediates: BAMs, coverage TSVs | large | gitignored `work/` `results/`; **regenerated by Nextflow** | the pipeline itself (rerun to reproduce) |
| Scored table, model bundles, dataset release | medium–large | **Zenodo** — the canonical, versioned, citable release (DOI) | DOI + `pixi.lock` + container digests + data manifest |
| App-served table | small→large | **Simplest-first:** static JSON in the Cloudflare Pages deploy while small; **Cloudflare R2** (free, zero egress) once it outgrows the 25 MB/file Pages limit | copied from the Zenodo release by CI |
| Oracle goldens, tiny test FASTQ / mini-reference | KB–MB | **plain git** | committed with the tests they anchor |

**GitHub↔Zenodo integration** auto-archives each tagged release, minting a version DOI — this is
the definition-of-done "scored table released with a DOI."

## Consequences

- The repo stays **code + tiny fixtures only**; clone is fast; the LFS cap is irrelevant.
- Reproducibility rests on *regeneration* (Nextflow + pinned deps + fetch scripts), not on stored
  bytes — the correct model for a scientific pipeline.
- `data/` is gitignored except its README; a fetch script must exist for every input, and every
  input carries a checksum. No manual "download and drop it in" steps that can't be reproduced.
- No DVC/git-annex: Nextflow already provides pipeline reproducibility, so a second data-versioning
  system would be redundant complexity.
